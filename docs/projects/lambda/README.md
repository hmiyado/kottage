# Lambda移行プロジェクト

## 概要

バックエンドの実行環境をEC2から「ECRのコンテナイメージで動くLambda」へ移行するプロジェクト。
public IPv4アドレス課金の撤廃と、EC2の死活監視という運用負荷の解消を目的とする。

## 背景: なぜpublic IPが不要にできるのか

現状のリクエスト経路を調査した結果、**public IPは受信には一切使われていない**ことが判明した。

```text
API Gateway → Lambda http_proxy (VPC内) → EC2のプライベートIP 10.0.0.198:8080
```

- セキュリティグループ `ec2_instance` のingressは `10.0.0.0/16` のみ。インターネットからの受信は閉じている
- EC2インスタンス本体は `associate_public_ip_address = false`。課金対象はEIP 1個だけ

EIPの実際の用途は次の2つしかない。

1. **EC2からのoutbound IPv4** — Docker Hubのpull、TiDB Serverlessへの接続、yum
2. **SSH管理アクセス** — `ec2-monitoring-checklist.md` に記録された障害対応で使用

AWSには無料のIPv4 egressが存在しない（public IP $3.65/月 か NAT Gateway $32/月）。
したがって**常時起動のEC2を保つ限りこの費用は消せない**。EC2そのものを廃止するのが唯一の解となる。

> **補足**: TiDB移行プロジェクトのREADMEにある「VPC (Lambda ENI): $3.72/月」という項目は、
> 実態としてはこのEIPのpublic IPv4課金（$0.005/h × 744h = $3.72）である。
> Lambda ENIのVPC接続自体には課金されない。本プロジェクトで撤廃する対象はこの項目にあたる。

## 目標

- **コスト削減**: 月$8.6（年$103）のEC2+EIP+EBS費用を削減
- **運用負荷の解消**: EC2の死活監視・自動復旧の仕組みが不要になる
- **リスク最小化**: 各工程でロールバック可能な状態を維持し、EC2は最後まで残す

## コスト比較

### 現状（us-east-2）

```text
EC2 t2.nano:            $4.23/月  ($0.0058/h × 730h)
EIP (public IPv4):      $3.65/月  ($0.005/h × 730h)
EBS gp2 8GB:            $0.80/月
Route 53:               $0.50/月
Lambda http_proxy:      $0/月     （無料枠内）
API Gateway HTTP API:   $0/月     （低トラフィックのため数セント）
TiDB Serverless:        $0/月     （無料枠内）
合計:                   約 $9.2/月
```

### 移行後

```text
Lambda (アプリ本体):     $0/月     （無料枠: 月100万リクエスト + 40万GB秒）
ECR ストレージ:          $0.05/月  （ライフサイクルポリシーで直近10世代のみ保持）
Route 53:               $0.50/月
API Gateway HTTP API:   $0/月     （変化なし）
TiDB Serverless:        $0/月
合計:                   約 $0.6/月

削減額: 約 $8.6/月（≒$103/年、93%削減）
```

> コスト値は us-east-2 の公開価格に基づく試算。実際の請求で検証すること。

## 移行後のアーキテクチャ

```text
[ブラウザ] ─https─> API Gateway HTTP API (kottage.miyado.dev)
                        │
                        ▼
                   Lambda（非VPC）
                   ├── lambda-adapter（拡張）
                   └── Ktor アプリ (127.0.0.1:8080)
                        │
                        ▼
                   TiDB Serverless (us-east-1)
```

**要点**: Lambdaを**VPCに入れない**ことでENIを持たせず、インターネットへのegressが無料になる。
これによりTiDBへの接続もNAT Gatewayなしで成立する。これが本設計の鍵。

## 主要な技術的判断

| 論点 | 判断 | 理由 |
|------|------|------|
| パッケージング | コンテナイメージ（ECR） | 既存Dockerfileをほぼ流用できる。Lambdaはコンテナイメージを ECR からのみ取得可能 |
| SnapStart | 使わない | コンテナイメージでは非対応。コールドスタートはフェーズ7で計測して判断する |
| Provisioned Concurrency | 使わない | 月$4-5かかり削減額を打ち消すため。採用するなら移行の前提が崩れる |
| VPC接続 | しない | ENIを持たせないことで無料のインターネットegressを得る |
| セッション保存 | 署名付きcookie（MACのみ、暗号化なし） | Lambdaは実行環境が複数並走するためサーバ側メモリは使えない。DynamoDBも不要になる。中身は `userId` とCSRFトークンのみで秘匿性が不要 |
| 有効期限 | `expiresAt` を署名対象に含める（絶対期限7日） | MACはペイロードを守るが期限を持たない。cookieの `maxAge` はクライアント側の値でありサーバーが強制できないため、期限自体を署名する |
| JWT | 導入しない | Ktorのセッション機構を維持する方が変更が小さい。既存の `java-jwt` 依存はGoogle OIDCトークン検証用であり別物 |
| CPUアーキテクチャ | arm64（Graviton） | Lambda料金が2割安くなる。イメージはマルチアーキ（amd64/arm64）でpushし、EC2での検証経路を維持する |
| cookie属性 | `Secure=true` / `httpOnly=true` に修正 | ステートレス化でcookie自体が資格情報になるため盗難対策の価値が上がる。既存TODOの「内部がHTTPだからsecureにできない」は誤診で、フロントもJSからcookieを読んでいない |
| シークレット管理 | Lambda環境変数（Terraform管理）。source of truthは `sensitive.tfvars` | Secrets Managerは1本$0.40/月で削減額の11%を消費するため使わない。SSM Parameter Store SecureString（無料）は代替候補 |

## リスク管理

| リスク | 深刻度 | 対策 | 判断フェーズ |
|--------|--------|------|-------------|
| JVMのコールドスタートが許容できない | **高** | フェーズ7で計測。不可なら案B（Lightsail移行、$3.5-5/月）へ切り替え | 7 |
| セッション/OAuthの退行 | **高** | フェーズ2を**現行EC2上で先行デプロイして本番検証**する | 2 |
| Flywayの同時実行 | 中 | フェーズ3で起動時処理から分離 | 3 |
| freeze/thawによるDB接続断 | 低 | フェーズ7.4で調査済み: HikariCP等のプーリングは未導入で、Exposedはtransaction毎に素のJDBC接続を張り直すため、freezeで壊れた接続を掴む故障モード自体が原理的に起きない。トレードオフはリクエスト毎のTCP/TLSハンドシェイクのレイテンシで、7の計測で許容範囲を判断する | 7 |
| API Gateway統合タイムアウト30秒上限 | 低 | Lambdaのtimeoutを29秒以下に設定 | 7 |

**最大のリスク低減策**: フェーズ2〜4のアプリ変更は、すべて**現行のEC2上で本番検証できる**。
Lambdaへの切り替え（フェーズ8）時点では、アプリの挙動は既に検証済みという状態を作る。

## 開発の進め方

TiDBプロジェクトとは異なり、**マージを待たずに後続フェーズの作業を進める**方針をとる。

### 原則

- **PRは工程（フェーズ）単位で出す**。1フェーズ = 1PR。複数フェーズを1つのPRにまとめない
- 各PRは人間（宮戸）のレビューを経てmainにマージする
- **PRのマージを待たずに後続フェーズの作業に着手してよい**。その場合は依存元のブランチから分岐する
- レビュー指摘で依存元が変わった場合は、後続ブランチをrebaseして追従する

### ブランチ命名規則

```text
feature/phase{N}-lambda-{description}
例: feature/phase1-lambda-remove-redis
```

### 依存関係と並行トラック

```text
トラックA（アプリ）   1 ──> 2 ──┐
                      └──> 3 ──┤
トラックB（イメージ/CI） 4 ──> 6 ──┤
                       5 ────────┤
トラックC（インフラ）              └──> 7 ──> 8 ──> 9
```

- フェーズ1・4・5は依存がなく即着手できる
- フェーズ2と3は互いに独立（触るファイルが異なる）
- フェーズ7はフェーズ2・3・5・6すべての成果が必要
  （**訂正**: 当初フェーズ5・6のみとしていたが、フェーズ2は機能検証（サインイン・
  OAuth）が意味を持つための前提であり、フェーズ3はコールドスタート計測を
  マイグレーション実行時間で汚染しないための前提として、いずれも実質的な依存だった。
  詳細は[移行計画（詳細版）](./migration-plan.md)のフェーズ7を参照）
